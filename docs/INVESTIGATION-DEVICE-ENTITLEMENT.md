# 调查：设备身份与整曲权益的关系（[#10](https://github.com/sodahub-org/libmssdk/issues/10)）

> 要回答的问题只有一个：**用服务自己生成的设备号去请求上游取流，为什么只拿到试听片段？**
>
> 结论先行：**服务自己生成的设备号不是那把锁。** 同一份 Cookie、同一首曲子，把设备号换成
> 毫秒时间戳、每轮全新的随机 16 位、服务落盘的固定 16 位，结果一模一样；其中一首有授权的曲目
> 甚至**完全不发 Cookie** 也照样整曲 6 档（含 lossless）。决定整曲与否的是**曲目本身的授权等级**，
> 不在设备身份层。
>
> 三条要说清的边界，别把结论读过头：
>
> - 票里原本要求的那一条对照（**抓包来的真实设备身份**）本次没跑——这台机器上没有官方 PC
>   客户端、也没有抓包件。证伪绑定说不需要它（推理见第四节 1），但**在试听级曲目上排除它**需要它。
> - 「当初扫的 7 首全是试听级」是**推断**：只逐首复测了其中 1 首，外加另一首同样只给试听的，
>   两首都稳定复现试听；剩下 5 首没复测。
> - Cookie 只测了**有无**，而且只在有授权的曲目上测；「缺哪个字段」这种具体形态没测。

---

## 一、三种解释各自要怎么被检验

调查开始前立了三种解释（也是这张票的原始表述），公开记录里同类症状绝大多数归因于前两种。
每一种都配一条**只有它成立时才会出现**的读数：

| 解释 | 如果成立，会看到 | 如果不成立，会看到 |
| --- | --- | --- |
| Cookie 不完整 | 带 Cookie 与不带 Cookie 结果不同 | 两者结果相同，且整曲照常出现 |
| 签名构造有误 | 回包是 `HTTP 200 + 0 字节`，或改了 headers 就空 | 回包是结构完整的 JSON（非空即代表服务端认了这个签名） |
| 签名设备 = 登录设备 | 只有「与账号登录设备一致」的设备号能拿整曲，随机设备号一律试听 | 随机设备号也能拿整曲 |

第一条要说清楚测到什么程度：`no-cookie` 测的是 Cookie 的**有无**，不是「少了哪个字段」，
而且只在**一首**有授权的曲目上测过。「字段不全」这个具体形态要拿一份已知完整的登录件与一份
缺字段的对照件比，本次没做（第七节）。所以这条对照只排除了一个较窄的情形：
在那首匿名也给整曲的曲目上，登录态不是决定项。它**没有**排除「Cookie 缺字段导致某些曲目降级」——
那正是「Cookie 不完整」这条解释的主张，本票没能对它做测量。

第三条最戏剧性，也最容易抢跑。票里原本要求的对照是「随机生成的设备身份 vs **抓包来的真实设备身份**」，
本次没有那份真实身份，改用一对必然不可能匹配任何登录设备的形状：
`good-ts`（每次请求换一个毫秒时间戳）与 `rand16`（每次运行换一个全新的随机 16 位）。
证伪只需要一个反例——绑定说的预言是「不匹配就不给整曲」，而随机设备号拿到了整曲，
这条预言就倒了；**证实**它才需要那份真实身份。所以矩阵里同时留了 `captured` 一条 arm
（`--device/--iid/--fp` 传入），谁有抓包件就能把票里原本那一条补跑：

```bash
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --arm captured \
     --device <抓包 device_id> --iid <install_id> --fp <fp>
```

`sig-mismatch` 是签名有效性对照：故意让 URL 里的设备号与签名器 `init()` 用的设备号不一致。
`no-sign` 是必要性对照：同样的请求不发签名。它决定上面所有读数能不能被解释成「签名被接受」——
没有它，「非空回包」这句话没有含义。

## 二、复现步骤

前置条件：

1. 本机 `vendor/soda-music/` 里有**你自己**客户端里的 `bdms.node` 与 `metasecml.dll`（不入库）。
2. 本机有一份你自己的登录 Cookie。默认从 `%APPDATA%/sodam/config.json` 的 `cookie` 字段读；
   也可以 `export LIBMSSDK_COOKIE='…'`（进程环境变量，不落盘）。
3. 两首曲目号：一首你在播放器里**确实听到过整曲**，一首**只听到过试听**。
   曲目号从你自己那边抄——例如 sodam 的音频缓存文件名就是 `<track_id>-<档位>.m4a`
   （Windows 在 `%LOCALAPPDATA%/sodam/audio/`）。
   不知道哪首算哪首时，先跑 `--arm seo-web`（免签名）看 `streamDurationSeconds`：
   落在 30 / 60 附近的就是试听级候选。该接口的 `track.duration` 是 0，
   所以它只能佐证试听长度，不能用 `fullTrack` 判整曲。
4. Cookie 来源默认按「环境变量 `LIBMSSDK_COOKIE` → 本机播放器配置」的顺序找；
   要指定别的来源用 `--cookie-from env`、`--cookie-from sodam` 或 `--cookie-from <文件路径>`
   （`.json` 会去读它的 `cookie` 字段，其它按纯文本整份当 cookie）。
   读不到时不会把本机路径打进日志。
5. 出网到 `api.qishui.com` 与 `beta-luna.douyin.com`。矩阵里的公共参数钉死了
   `region=cn` / `geo_region=cn` / `os_version=Windows 11` / `tz_name=Asia/Shanghai`——
   从别的地区或别的平台形态跑，先把这几项改准，否则地域/平台授权会先于你想测的变量把结果定死。
   上游超时默认 15 秒，用 `LIBMSSDK_UPSTREAM_TIMEOUT_MS` 调；`--track` 也可以用
   `LIBMSSDK_PROBE_TRACK_ID` 提供。

**正对照建不起来怎么办**：如果你手上任何一首曲子在 `good-ts` 下都只有试听，那本实验的基线无法建立，
此时**不能**得出「设备号无关」——那说明问题在账号权益或上游侧，需要换一个已知有整曲授权的账号重跑。
本次是在基线成立（`good-ts` 拿到整曲）的前提下读出后面那些结论的。

```bash
# 只打印矩阵，不打网络
node tools/entitlement-matrix.mjs --list

# 正对照：应当是整曲。这一条不过，后面所有读数都没有意义
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --arm good-ts

# 一次跑完（不给 --device 时自动跳过 captured：9 条签名请求 × 2 轮 + 1 条免签名）
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --repeat 2

# 票里原本那一条：手上没有抓包身份就跳过这步
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --arm captured \
     --device <抓包 device_id> --iid <install_id> --fp <fp>

# 关键的一条：把曲目换成「只有试听」的那首，其余一切不动
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm good-ts
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm service-id
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm no-cookie

# 必要性对照：不发签名
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --arm no-sign
```

每条 arm 与 `good-ts` 基线之间**只允许动它声明出来的那几个字段**，这条不变量由
`test/entitlement-matrix.test.mjs` 离线守住（改一个字段就测不出来是谁在决定权益）。
请求预算：整份矩阵跑两轮约 18 次签名调用；本次实跑 26 次签名请求 + 3 次免签名
（超出最初估的 15–25 次，多出来的都花在跨曲目复测上），所以 §三 的读数表比矩阵少几条。

### 判据

| 读数组合 | 判定 |
| --- | --- |
| `good-ts` 试听 | 实验本身不成立（复刻不了已知会成功的那条请求），先查形状，不要往设备号上想 |
| 同一首整曲曲目下，`rand16` / `service-id` / `no-cookie` 都是整曲 | 设备号与 Cookie 的有无在这类曲目上不是变量 |
| `no-sign` 是 `200 + 0 字节` | 上面那些「非空回包」确实等于签名被接受 |
| 曲目 A 在所有 arm 下整曲、曲目 B 在所有 arm 下试听 | 决定因素落在曲目层，不在被换掉的那几个凭据维度上 |
| **试听级曲目 B** 上，`captured`（真实登录设备）给整曲、随机设备号给试听 | 绑定说在「需要权益的曲目」上成立——本次没跑这一格 |
| 只有匹配登录设备才给整曲、随机设备号一律试听（在有授权的曲目上） | 绑定说成立（**本次没出现**） |

倒数第二行是这张表原本缺的一格：本次的证伪只发生在「匿名也给整曲」的曲目上，
那里根本没有登录设备可言；要在**试听级**曲目上排除绑定说，只能靠 `captured` 那一格。

**`captured` 那一格怎么拿到匹配身份（本票没跑，也没验证过这条路径）**：不需要装官方 PC 客户端，
也不需要代理抓包。libresoda 的扫码登录每次会为这个会话随机生成一个 16 位 `device_id`
（`qr_login.rs` 的 `session.device_id`），并且**设置 `SODA_QR_STATE=<路径>` 时这份会话会被写进那个文件**——
也就是说，登录用的设备号本来就在我手上，只是登录后被丢掉了。流程大致是：
给播放器（或任何调用 `create_qr` 的程序）设上 `SODA_QR_STATE`，扫一次码，
从状态文件里读回那份 `device_id` / `install_id`，再用它跑 `--arm captured`。
两点要提醒：这条路径**本票没有实测**，而且它依赖一个还没验证的前提——上游是否真按那个
`device_id` 参数登记这次会话的设备；写在这里只是把缺口标注成可执行的动作，不是可依赖的配方。
另外登录产生的新会话会顶掉播放器里存的那份 Cookie，做之前先备份配置。
扫码登录依赖签名页（Chromium），纯 HTTP 直连护照接口会被限流。

## 三、本次读数

环境：Windows 原生 Node + 本机 `vendor/soda-music/bdms.node`；同一份 Cookie；2026-10-28。
签名只记长度（`X-Helios` 48，`X-Medusa` 828–840），设备号只留首尾。

### 同一首「已知能拿到整曲」的曲目，换着花样动凭据

| arm | 改动 | 结果 |
| --- | --- | --- |
| `good-ts` | 基线：设备号=毫秒时间戳（每次不同） | **整曲** 6 档，含 lossless/flac |
| `rand16` | 只换成两个全新的随机 16 位设备号（两轮） | **整曲** 6 档 |
| `service-id` | 只换成本服务落盘的那一份固定 16 位 | **整曲** 6 档 |
| `probe-shape` | `probe` 用的身份 + 版本号 + local-user（3.8.0 / `local-user: 0` / 服务身份） | **整曲** 6 档 |
| `app380` | 只把版本号与 UA 推到 3.8.0 | **整曲** 6 档 |
| `localuser0` | 只把 `x-luna-is-local-user` 从 1 改成 0 | **整曲** 6 档 |
| `no-cookie` | 只不发 Cookie | **整曲** 6 档 |
| `sig-mismatch` | URL 用时间戳设备号，签名器 `init()` 用另一个随机 16 位 | **整曲** 6 档 |
| `no-sign` | 同样的请求，不发 `x-helios` / `x-medusa` | `HTTP 200 + 0 字节` |

`rand16` 两轮的设备号与 `service-id`、`good-ts` 全都不同，结果一致。
`probe-shape` 复刻的是当初扫 7 首全试听时用的那份**设备号 + 版本号 + local-user**，
今天在同一首整曲曲目上是整曲；但 `src/probe.mjs` 实际还多发 `x-tt-trace-id` 与 `accept-encoding`，
这一条没把那两个头带上，所以它**不等于替 shipped probe 的完整请求背书**（第七节）。

本次**没有**对试听样曲目跑 `rand16` / `no-cookie` / `sig-mismatch` / `captured`（预算已经超出最初的
15–25 次估算，多出来的都花在跨曲目复测上）。第二张表因此只有两种设备号形状，见第七节第一条。

### 换曲目，其余一切不动

| 曲目 | 曲长 | `good-ts`（时间戳） | `service-id`（固定 16 位） |
| --- | --- | --- | --- |
| 整曲样曲目 1 | 185.3 s | 整曲 6 档（lossless 1572 kbps） | 整曲 6 档 |
| 整曲样曲目 2 | 109.0 s | 整曲 6 档 | 整曲 6 档 |
| 试听样曲目 1 | 278.5 s | 60 s 试听，仅 `higher` 1 档 | 60 s 试听，仅 `higher` 1 档 |
| 试听样曲目 2 | 292.7 s | 30 s 试听，仅 `higher` 1 档 | 30 s 试听，仅 `higher` 1 档 |

试听样曲目 1 正是当初 Wine 原型里逐首扫到的那一首（60 s / 278.5 s），
两种设备号形状读数相同；免签名的 `seo-web` 对同一首回包里 `video_duration` 也是 60.001，
也就是免签名接口早把它当试听级发出来了。
（`seo-web` 的回包结构不同，本票不拿它判整曲，只用它佐证「试听长度」这个观察。）

### 不打上游的旁证：本机播放器自己的缓存

同一个账号、同一台机器、同一个签名器，播放器走的正是「设备号 = 每请求一个毫秒时间戳」那条路径。
它的缓存条目带着播放器自己算出来的 `preview` 标记（曲目号与曲名不外传，只给计数）：

| 缓存条目 | 播放器判定 | 数量 | 中位体积 |
| --- | --- | --- | --- |
| 全部 | — | 406 | — |
| 整曲 | `preview=0` | 139 | 2.24 MB |
| 试听 | `preview=1` | 267 | 0.97 MB |

也就是说 **139 首整曲是在「设备号每请求都不同」这个条件下拿到的**，而同一条件下另有 267 首只有试听。
样本比上面那 4 首的对照大两个数量级。但它**不是对照实验**：没有控制任何变量，
它只能说明「同一套凭据条件下两种结果并存」，与「决定因素在曲目层」一致。

### 一条容易误用的字段

`track.label_info.only_vip_download` 在**整曲曲目和试听曲目上都为 `true`**，
不能拿它判断「这首曲子这个账号能不能听整曲」。能判定的只有
`video_model.video_duration` 与 `track.duration` 的关系（也就是 `probe` 现在用的
`fullTrack` 判据）。

> 上表四首曲目的曲目号只留在本机，不入库——它们能反出个人收听记录。
> 结论不依赖具体曲目号：换成你自己的「一首已知整曲 + 一首已知试听」照第二节跑一遍即可。

## 四、结论

1. **「签名设备必须与账号登录设备一致」这条假说，在实测范围内不成立。**
   它的预言是「设备号与登录设备不一致 ⇒ 不给整曲」。反例有四个，都落在同一首有授权的曲目上：
   每次请求都不一样的毫秒时间戳、每轮都不同的随机 16 位、服务落盘的固定 16 位——这三个值都不可能
   等于任何一台真实登录设备——都拿到了整曲；甚至**根本不发 Cookie**（这时候压根没有登录设备可言）
   也拿到了整曲。一个反例就足以推翻它的普遍形式，所以证伪不需要「抓包来的真实身份」。
   **但要说清这个反例证伪到了哪一层**：它只出现在「本来就肯给整曲」的曲目上。
   在两首试听级曲目上，本次跑过的两种设备号同样都不是登录设备，所以「两首都试听」
   跟绑定说**并不矛盾**——要把绑定说在那些曲目上也排除掉，只有 `captured` 那一格能做到（第七节）。
2. **Cookie 的有无，在有授权的曲目上不是变量。** 同一首曲目的整曲结果在带 Cookie 与
   完全不带 Cookie 时相同。注意测的是**有无**、不是「缺哪个字段」，而且这组对比没在试听级曲目上做过：
   「Cookie 不完整」这个具体形态仍然没被直接测过（第七节）。
   也就是说，这条读数排除的是「Cookie 决定整曲与否」，没有排除「Cookie 缺字段导致某些曲目降级」。
   能确定的是：**同一份 Cookie 下，A 曲目整曲、B 曲目试听**——这个差异不在凭据侧。
3. **「签名构造有误」不成立。** 所有带签名的 arm 都拿到结构完整的回包；
   唯独 `no-sign` 拿到 `HTTP 200 + 0 字节`。这既说明签名确实被校验，也说明
   「非空回包 = 签名被接受」这个推理在本接口上成立。
4. **真正的原因是曲目层面的授权差异。** 同一份凭据、同一个签名器、同一台机器下，
   两首曲目给出整曲全部档位（185.3 s / 109.0 s），两首只给 30–60 秒单档试听，
   且每首的结果与设备号形状无关。两轮重复只落在第一张表那首曲目上（矩阵跑了 `--repeat 2`）；
   第二张表的四种读数各跑一次。本机播放器缓存里那 406 条（139 首整曲 / 267 首试听，
   全部产生在「设备号每请求一变」的条件下）给的是同一个方向，虽然它不是对照实验。
   至于当初那 7 首：**推测**全部落在试听级这一侧——逐首复测的只有其中 1 首，
   另外 5 首没复测（第七节）。但本票要回答的那件事已经有答案了：
   **不是服务自己生成的设备号造成的。**

**本票还不能按「定案」关闭。** 票里那句「为什么只能拿到试听」的正面答案（曲目授权）目前靠
一条推断 + 一条非受控旁证支撑，而唯一能同时补齐「绑定说在试听级曲目上是否成立」和
「Cookie 缺字段是否是降级原因」的实验（`captured` 跑在一首试听级曲目上）还没跑——
手上没有抓包身份。要合上它，需要任意一个熟悉的人拿自己的抓包件补那一格即可，脚本入口已经留好。

一张票只负责分清责任。本票要回答的那件事有明确答案：**不是服务自己生成的设备号造成的**——
同一份设备号在别的曲目上照样拿到整曲。责任既不在本仓库，也不在客户端落到 URL 里的那个时间戳
（第六节那条是独立缺陷，与本票结论没有因果关系）。上游对「哪首曲子能给整曲」的判定本票不往下追
（会员层级 / 地区授权 / 单曲购买，具体是哪一种需要另一份带已知权益账号的对照）。

### 顺带被削弱的一条既有说法

`sig-mismatch`（URL 设备号与签名器设备号不一致）没有被拒。但**不能就此证明上游不校验设备一致性**：
那首曲目在不带 Cookie、不带任何一致性时本来就是整曲，这条对照没有区分力。
要真正证伪「成套」要求，需要一首「只有成套才给整曲」的曲目，本次没有找到。
本仓库继续按「签名器与 URL 用同一份设备号」实现是自洽且更省事的（避免每请求重新 `init()`），
只是**不该再把它当成上游的强制要求来写文档**。

## 五、多人共享同一份设备身份的后果

票里这条判据的前提（设备绑定）没有成立，所以这里回答的是「既然不绑定，共享身份意味着什么」。

- **权益角度：在本票实测范围内没有后果。** 整曲与否与设备号无关（在会给出整曲的曲目上），
  共享一份身份既不会让谁的权益变差，也不会让任何人凭共享身份多拿到什么。
  边界照旧要说一句：试听级曲目上「换一个身份能不能变整曲」本票没测（判据表与第七节都留了那一格），
  所以这里说的是「共享身份不会让本来能拿到的整曲拿不到」，不是「身份怎么都无所谓」。
  反过来说，**设备身份不是访问控制**，不要指望用「每人一个设备号」来限制谁能拿到整曲。
- **上游视角下的风险：风险变大了，且集中在签名器这一台机器上。**
  签名即凭据、且账号 Cookie 不是必要变量，意味着「一个签名器 + 一个出口 IP + 一个设备号」
  可以为任意多人取任意有授权的整曲。上游看到的画像是「同一个设备号高频请求大量不同曲目」——
  这是最典型的爬虫特征，被风控时受影响的是这台签名器与它的 IP，而不是某个用户。
  这正是本仓库总纲里「删掉会替别人打上游的诊断接口、按 IP 分桶限流」那两个决定的理由所在。
- **可接受的共享形态**：一个签名器只服务一小撮可预期的人（家庭/小团队），
  并把速率限制在自己的容量与画像可解释的范围内。公开池化一台签名器，等于把自己的 IP
  押上去替所有人承担风控。

## 六、确实指向客户端的那件事（与本票结论无关，但是独立缺陷）

调查过程中在代码层面确认了一件事。先说清楚：它**不是**试听问题的原因（第四节 1 已经排除），
所以本票的结论不依赖它；但它是一个独立存在的缺陷，归属在那两个客户端仓库，
本票只负责把它记下来，**改法由那两个仓库决定**。

- `libresoda` 的 `device_id` / `iid` / `fp` 配置项默认为空，空值会落到
  `Date.now()` 与 `Date.now()+1`（见该仓库 `src/soda/mod.rs` 的 `pc_app_params_with`），
  于是**每个请求的设备号都不一样**；`sodam` 的设置界面没有这三个字段可填，
  所以普通用户一直走的是这条回退路径（本机日志里能直接看到 `device_id=""`）。
- 会造成的影响有两层，都属于「画像」而不是「权益」：
  一是上游会看到「同一台机器、同一 Cookie、设备号每请求一变」；
  二是签名器每次都要重新 `init()`（本仓库 `src/bdms.mjs` 按设备号变化重新初始化），
  而按早前原型的观察，`init()` 之后有一段「短签名窗口」。
  本次读数里 `X-Medusa` 多数落在 828、少部分是 840——**本票没有把这组长度归因到那个窗口**：
  矩阵里每条 arm 都先签一次丢掉、只用第二次的那一份（`signWarmedUp`），
  所以这些长度到底是窗口尾部还是稳态，本次的对照设计测不出来。
  能说的只有一句：这些签名全部被上游接受了，但那只覆盖 `track_v2` 一条接口。
- 要动哪儿，供那两个仓库参考（不是本票的决定）：`sodam` 缺一个能持久化设备身份的入口；
  `libresoda` 的空值回退目前产生「每请求新值」，而这个值本不需要每请求都换。
  至于应该「每进程一个」「落盘一个」还是「缺了就拒绝并提示」，那是那边的接口设计，本票不预判。

## 七、未决项

- 票里原本那条对照——**抓包来的真实设备身份**——没跑（这台机器没有官方 PC 客户端、没有抓包件）。
  入口已经留在 `--arm captured --device/--iid/--fp`；结论不依赖它（见第四节 1 的证伪逻辑），
  但「在**试听级**曲目上排除绑定说」这一件事只能靠它，本次做不到。
- 上面那条「用 `SODA_QR_STATE` 拿回扫码登录会话设备号」的路径本身也没实测，
  且依赖「上游按那个参数登记会话设备」这个未验证前提。
- 试听样曲目只测了两种设备号形状：`rand16` / `no-cookie` / `sig-mismatch` 没在试听级曲目上跑过。
  「试听级曲目带不带 Cookie 也一样」目前是**外推**，不是测量。
- 「Cookie 字段不全」这个具体形态没测（只测了有无）。
- `probe-shape` 只复刻了 shipped probe 的身份 / 版本号 / local-user，没带上它的
  `x-tt-trace-id` 与 `accept-encoding`；要替 `probe` 本身背书，得再补一条带这两个头的 arm。
- `captured` 只给 `--device` 时 `iid` / `fp` 会被 `device_id` 顶上（脚本会打一行提醒）——
  那不是一份完整的抓包身份，跑出来的读数不能直接当「真实设备身份」的结果读。
- 曲目层的授权具体由什么决定（会员层级 / 地区 / 单曲购买）——需要一个已知权益的账号做对照。
- 「只有成套才给整曲」的曲目是否存在，即上游到底校不校验设备一致性——见第四节末。
- 当初那 7 首里有 5 首没逐首复测（第四节 4）。
- 其它接口（不止 `track_v2`）上签名有效性是否同样宽松。
- 输出脱敏覆盖到的形态有离线测试钉住（带空格的用户名、`Program Files`、无冒号的容器路径、
  盘根、首段带空格的 posix、单段路径、UNC）。代价是相对路径也会被一并隐掉——诊断时少点线索，
  换的是日志可以放心外贴。
- `probe` 的试听提示文案按本结论改掉了「设备指纹不匹配」这一归因；
  若日后发现能判定的字段，应把提示改成可行动的那一句。
- **已收口**（不是未决，记在这儿是因为它改了上一轮的取数环境）：对照实验在 Docker + Wine 容器里
  **能跑**（#30）。上一轮记成「这条路不支持」，实测原因相反——卡点是二进制的挂载位置：
  `bdms.node` / `metasecml.dll` 放在 `/mnt/*` 这类 drvfs 绑定挂载上，Wine 会停在 `require` 里
  不返回，安静、无报错，`init` 与签名两层根本没开始（分层探针读到的形状与全部实测数字写在
  `verify/wine-multi/README.md` 的「已知的环境坑」；想知道自己那次卡在哪一层就跑
  `verify/wine-multi/bdms-layers.mjs`）。决定成败的只有二进制在哪，两种形状都测过：脚本留在
  drvfs 上、二进制进容器自己的文件系统——三层 1.5–3.2 秒走完；整个仓库连同二进制 `docker cp`
  进容器——本工具跑完一条 arm（`--arm good-ts`，曲目号当场编的、`--cookie-from /dev/null` 即匿名），
  签名链路走完、上游回了 `HTTP 200` 非空回包。**这一条只是通路验证，不是权益读数**：合成曲目号
  与匿名 cookie 下 `fullTrack` 本来就该是 false，别把它当成一条新的权益读数。
  本报告的权益读数仍出自本机 Windows 原生 Node，与容器里是同一个 `bdms.node`——换到容器里重跑
  同样的 arm 属于复现，不构成新的对照（真要新增对照的是第七节前面那几条）。

## 八、敏感边界

- Cookie 只在本机进程内使用，不写盘、不打日志、不进任何输出文件；输出里只出现「几个字段」。
- 签名值只记长度；设备号只留首尾三位；曲目号只留末四位、曲名不输出
  （`tools/entitlement-matrix.mjs` 的读数默认就是脱敏的，日志可以直接贴进票里）。
- 连报错都做了脱敏：`bdms.node 不存在：<本机绝对路径>` 这类信息在输出里只留失败步骤，
  绝对路径整段隐掉（Windows、容器里无冒号的 posix 路径、首段带空格的路径都覆盖）。
- 本文不含任何曲目号、Cookie、签名值或完整设备号；读数只说明响应形状。
- 把这份结论贴到 issue / PR 时，同样不要带 Cookie、签名值、完整设备号或本机路径。
