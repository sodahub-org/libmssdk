# 调查：设备身份与整曲权益的关系（[#10](https://github.com/sodahub-org/libmssdk/issues/10)）

> 要回答的问题只有一个：**用服务自己生成的设备号去请求上游取流，为什么只拿到试听片段？**
>
> 结论先行：**服务自己生成的设备号不是那把锁。** 同一份 Cookie、同一首曲子，把设备号换成
> 毫秒时间戳、每轮全新的随机 16 位、服务落盘的固定 16 位，结果一模一样；其中一首有授权的曲目
> 甚至**完全不发 Cookie** 也照样整曲 6 档（含 lossless）。决定整曲与否的是**曲目本身的授权等级**，
> 不在设备身份层。
>
> 2026-11-03 把票里原本缺的那最后一格补上了，结论没有翻：抓包来的真实身份（本机已登录播放器
> 在网线上实际发的那一份）打在两首试听级曲目上仍然是 30 / 60 秒单档，同一份身份打在
> 一首有授权的曲目上照样整曲 6 档。而抓包本身给出了更靠前的一件事：
> **抓到的那 6 条业务请求，每条都换一个 13 位毫秒时间戳——本机这条链路上没有一份可称作
> 「登录设备」的稳定身份。** 服务端有没有替这个账号登记过别的设备，本票没有可查的入口（第七节）。
> 这一格里 `captured` 与 `good-ts` 本来就同形（真机发的就是时间戳），所以它不构成新的区分力；
> 把最后一格收口的是上一句——绑定说缺的是主语，不是对照。
>
> 四条要说清的边界，别把结论读过头：
>
> - 票里那条「抓包来的真实设备身份」现在跑过了，但它抓到的不是官方 PC 客户端，而是本机的
>   sodam 播放器（`libresoda` 系）——官方客户端这台机器上没装。它已经是**这个登录态实际在用的**
>   那份身份，只是不等于「官方客户端的设备号」。
> - 「当初扫的 7 首全是试听级」仍是**推断**：逐首复测过的只有其中 1 首；补跑又新增两首
>   试听级样本，两首都是稳定试听，剩下 5 首没复测。
> - Cookie 测的是**有无**（有授权曲目与试听级曲目都测了）；「缺哪个字段」这种具体形态没测。
> - 曲目层的授权这次读到了两个对得上的字段（`only_vip_playable` 与账号的 `is_vip`），
>   但因果还差一份已知会员账号在同一批曲目上的对照（第七节）。

## 一、三种解释各自要怎么被检验

调查开始前立了三种解释（也是这张票的原始表述），公开记录里同类症状绝大多数归因于前两种。
每一种都配一条**只有它成立时才会出现**的读数：

| 解释 | 如果成立，会看到 | 如果不成立，会看到 |
| --- | --- | --- |
| Cookie 不完整 | 带 Cookie 与不带 Cookie 结果不同 | 两者结果相同，且整曲照常出现 |
| 签名构造有误 | 回包是 `HTTP 200 + 0 字节`，或改了 headers 就空 | 回包是结构完整的 JSON（非空即代表服务端认了这个签名） |
| 签名设备 = 登录设备 | 只有「与账号登录设备一致」的设备号能拿整曲，随机设备号一律试听 | 随机设备号也能拿整曲 |

第一条要说清楚测到什么程度：`no-cookie` 测的是 Cookie 的**有无**，不是「少了哪个字段」——
第一轮只在一首有授权的曲目上测过，补跑把同一组对照放到一首试听级曲目上（同读数）。
「字段不全」这个具体形态要拿一份已知完整的登录件与一份缺字的对照件比，两轮都没做（第七节）。
所以这条对照排除了一个较窄的情形：匿名也能拿整曲的那首曲目上，登录态不是决定项；
试听级曲目上带不带 Cookie 也一样。它**没有**排除「Cookie 缺字段导致某些曲目降级」——
那正是「Cookie 不完整」这条解释的主张，本票没能对它做测量。

第三条最戏剧性，也最容易抢跑。票里原本要求的对照是「随机生成的设备身份 vs **抓包来的真实设备身份**」。
第一轮（2026-10-28）手上没有那份真实身份，改用一对都不是任何固定身份的形状：
`good-ts`（每次请求换一个毫秒时间戳）与 `rand16`（每次运行换一个全新的随机 16 位，两轮互不相同）。
证伪只需要一个反例——绑定说的预言是「不匹配就不给整曲」，而这两个形状都拿到了整曲，
这条预言就倒了；**证实**它才需要那份真实身份。要说一句下限：这两个值会不会正好等于服务端替这个账号
登记过的某台设备，本票没有可查的入口（第七节）——但 `rand16` 每轮都换一个全新值、两轮都给整曲，
这已经是「必须固定匹配」这条预言能被打掉的最强形式。这一格在 2026-11-03 补上了，
抓法与读数分别在第二节与第三节；补之前留下的入口 `--arm captured` 现在默认从抓包件取值：

```bash
node tools/entitlement-matrix.mjs --track <曲目> --arm captured --from-capture <抓包件>
```

用的是件里哪一份，启动行与 `captured` 的读数都会报出来（`第 x 行`、那条的 `at`，
`at` 不像 ISO 时刻时写「未记时间」；行号按文件里的物理行算，空行也占一个号）。
行数口径是「共 N 行，空行 B 条，不是记录的行 S 条，没有 `device_id` 的记录 D 条」，为 0 的段不打印——
「共 N 行」是文件的行数，不是能当记录用的条数，两边的差只有把这些数报出来才对得上。

先说这一格量到了什么：抓回来的 `device_id` 本身就是每请求一个毫秒时间戳，所以 `captured`
与 `good-ts` 同形，**它对「绑定说」没有新的区分力**；有分量的是抓包这件事本身——
这个登录态没有一份可称作「登录设备」的稳定身份（第三节第一条）。

`sig-mismatch` 是签名有效性对照：故意让 URL 里的设备号与签名器 `init()` 用的设备号不一致。
`no-sign` 是必要性对照：同样的请求不发签名。它决定上面所有读数能不能被解释成「签名被接受」——
没有它，「非空回包」这句话没有含义。

## 二、复现步骤

前置条件：

1. 本机 `vendor/soda-music/` 里有**你自己**客户端里的 `bdms.node` 与 `metasecml.dll`（不入库）。
2. 本机有一份你自己的登录 Cookie。默认从 `%APPDATA%/sodam/config.json` 的 `cookie` 字段读；
   也可以 `export LIBMSSDK_COOKIE='…'`（进程环境变量，不落盘）。
3. 两首曲目号：一首你在播放器里**确实听到过整曲**，一首**只听到过试听**。
   曲目号从你自己那边抄——例如 sodam 的音频缓存文件名就是 `<track_id>-<档位>.m4a`
   （Windows 在 `%LOCALAPPDATA%/sodam/audio/`）。
   不知道哪首算哪首时，先跑 `--arm seo-web`（免签名）看 `streamDurationSeconds`：
   落在 30 / 60 附近的就是试听级候选。该接口的 `track.duration` 是 0，
   所以它只能佐证试听长度，不能用 `fullTrack` 判整曲。
4. Cookie 来源默认按「环境变量 `LIBMSSDK_COOKIE` → 本机播放器配置」的顺序找；
   要指定别的来源用 `--cookie-from env`、`--cookie-from sodam` 或 `--cookie-from <文件路径>`
   （`.json` 会去读它的 `cookie` 字段，其它按纯文本整份当 cookie）。
   读不到时不会把本机路径打进日志。
5. 出网到 `api.qishui.com` 与 `beta-luna.douyin.com`。矩阵里的公共参数钉死了
   `region=cn` / `geo_region=cn` / `os_version=Windows 11` / `tz_name=Asia/Shanghai`——
   从别的地区或别的平台形态跑，先把这几项改准，否则地域/平台授权会先于你想测的变量把结果定死。
   上游超时默认 15 秒，用 `LIBMSSDK_UPSTREAM_TIMEOUT_MS` 调；`--track` 也可以用
   `LIBMSSDK_PROBE_TRACK_ID` 提供。

**正对照建不起来怎么办**：如果你手上任何一首曲子在 `good-ts` 下都只有试听，那本实验的基线无法建立，
此时**不能**得出「设备号无关」——那说明问题在账号权益或上游侧，需要换一个已知有整曲授权的账号重跑。
本次是在基线成立（`good-ts` 拿到整曲）的前提下读出后面那些结论的。

```bash
# 只打印矩阵，不打网络
node tools/entitlement-matrix.mjs --list

# 正对照：应当是整曲。这一条不过，后面所有读数都没有意义
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --arm good-ts

# 账号自己是什么档位（免签名，不需要 --track）
node tools/entitlement-matrix.mjs --arm account-me
# 上面那条的匿名对照：这条回包解析不出用户 id，才说明上一条认的是登录态
# 实测读数：HTTP 200、157 字节、status_code 1000016、hasUser=false，退出码 1
# ——这条「跑对了」就是以非零码退出，别把它当成工具坏了
node tools/entitlement-matrix.mjs --arm account-me --cookie-from <一个空的文本文件>
# 别把这个文件命名成 .json：空内容过不了 JSON.parse，会被报成「--cookie-from 指定的文件读不到」（退出码 2）

# 一次跑完（不给 --from-capture 时自动跳过 captured：每轮 11 条上游请求 × 轮数）
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --repeat 2

# 票里原本那一条：先按第二节「captured 那份身份怎么拿」抓出那份文件，再喂进来
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --arm captured --from-capture <抓包件>

# 关键的一条：把曲目换成「只有试听」的那首，其余一切不动
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm good-ts
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm service-id
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm rand16
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm no-cookie
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm sig-mismatch
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm captured --from-capture <抓包件>

# 必要性对照：不发签名
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --arm no-sign
```

每条 arm 与 `good-ts` 基线之间**只允许动它声明出来的那几个字段**，这条不变量由
`test/entitlement-matrix.test.mjs` 离线守住（改一个字段就测不出来是谁在决定权益）。
请求预算：矩阵 12 条 arm，每轮发 12 条上游请求，其中 9 条带签名——每条先签一次丢掉、
只用第二次那一份，所以是 18 次签名调用；不给 `--from-capture` 时 `captured` 被跳过，
每轮就是 11 条请求、16 次签名调用，跑两轮 22 条请求。2026-10-28 那轮实跑 26 条签名请求
加 3 条免签名（超出最初估的 15–25 次，多出来的都花在跨曲目复测上），所以 §三 的读数表比矩阵少几条。
2026-11-03 的补跑是 9 条带签名请求（18 次签名调用）加 3 条免签名（`seo-web` 一次、
`account-me` 两次——第二次就是那条匿名对照），每条 arm 各跑一次、不做 `--repeat`。

### 判据

| 读数组合 | 判定 |
| --- | --- |
| `good-ts` 试听 | 实验本身不成立（复刻不了已知会成功的那条请求），先查形状，不要往设备号上想 |
| 同一首整曲曲目下，`rand16` / `service-id` / `no-cookie` 都是整曲 | 设备号与 Cookie 的有无在这类曲目上不是变量 |
| `no-sign` 是 `200 + 0 字节` | 上面那些「非空回包」确实等于签名被接受 |
| 曲目 A 在所有 arm 下整曲、曲目 B 在所有 arm 下试听 | 决定因素落在曲目层，不在被换掉的那几个凭据维度上 |
| **试听级曲目 B** 上，`captured`（真机发的那份）给整曲、随机设备号给试听 | 绑定说成立——**补跑过，没出现**；这一格的区分力见下面一段 |
| 只有匹配登录设备才给整曲、随机设备号一律试听（在有授权的曲目上） | 绑定说成立（**两轮都没出现**） |

倒数第二行就是这张表原本缺的那一格，这次补跑了，抓法见下一小节，读数在第三节。
**但这一格按票里的写法测不出新东西**，原因在读数本身：真机在网线上发的 `device_id` 就是
每请求一个毫秒时间戳，所以 `captured` 与 `good-ts` 是同一个形状，它落在试听级曲目上必然还是试听。
把这一格关掉靠的不是「又一种身份没翻盘」，而是**这台机器上根本没有一份可称作「登录设备」的稳定身份可试**——
绑定说的预言需要一个主语，实测到的是这个账号的主语不存在（第三节第一条）。
再往前一步缺的是两样东西，别混成一件：一是给「固定 vs 变化」补上真实主语——需要一台**会发固定
设备号**的客户端（官方 PC 客户端，或填了 `SODA_DEVICE_ID` 的）；二是「成套」那条要求需要一首
**只有成套才给整曲**的曲目（第四节末）。本机两样都没有，见第七节。

### `captured` 那份身份怎么拿（这条已实测）

不需要装根证书，也不需要改 hosts。播放器与签名器之间走的是明文 HTTP：`/sign` 收到的
就是播放器真实准备发出去的那条 URL，设备号在签名请求里现交出来。

```bash
# ① 本机起一台中转，只绑回环，把请求原样转发给播放器本来在用的那个签名器
node tools/signer-tee.mjs --upstream <播放器现在用的 /sign 地址> --out <仓库外的路径>
# ② 把播放器的 signer_url 指到 http://127.0.0.1:18899/sign，随便播一首（或让它自己把队列跑起来）
# ③ Ctrl+C 停掉中转，把 signer_url 改回原来那一份
# ④ 喂给矩阵：设备号走文件，不上命令行、不进 shell 历史
node tools/entitlement-matrix.mjs --track <试听级曲目> --arm captured --from-capture <上面那份文件>
```

落盘的只有时间、方法、路径、URL 里的 `device_id` / `iid` / `fp`、几个决定形状的公共参数、
请求头名与 Cookie 的**字段数**；Cookie 与 `Authorization` 的值、`x-helios` / `x-medusa` 都不写。
`--out` 指到仓库目录里会被直接拒——真实设备号属于不入库的那一类（第八节）。

早先记在这一节的另一条路（给扫码登录设 `SODA_QR_STATE`，再从状态文件捞回那份 `device_id`）
**不用走**：抓到的那 6 条业务请求用的都不是那份身份（第三节「真机在网线上发的是什么」）。

## 三、本次读数

环境：Windows 原生 Node + 本机 `vendor/soda-music/bdms.node`；同一份 Cookie；2026-10-28。
签名只记长度（`X-Helios` 48，`X-Medusa` 828–840），设备号只留首尾。
2026-11-03 的补跑（第三节最后两小节）用的是同一台机器、同一份环境与同一个签名器；
先试过在 WSL 的 `libmssdk` 容器（Wine + Windows 版 Node）里跑，第一次调用签名就挂住
（6 分钟无输出，`timeout 180` 也切不断），那批读数因此没有产出，见第七节「WSL 容器里第一次调用签名会挂住」那条。

### 同一首「已知能拿到整曲」的曲目，换着花样动凭据

| arm | 改动 | 结果 |
| --- | --- | --- |
| `good-ts` | 基线：设备号=毫秒时间戳（每次不同） | **整曲** 6 档，含 lossless/flac |
| `rand16` | 只换成两个全新的随机 16 位设备号（两轮） | **整曲** 6 档 |
| `service-id` | 只换成本服务落盘的那一份固定 16 位 | **整曲** 6 档 |
| `probe-shape` | `probe` 用的身份 + 版本号 + local-user（3.8.0 / `local-user: 0` / 服务身份） | **整曲** 6 档 |
| `app380` | 只把版本号与 UA 推到 3.8.0 | **整曲** 6 档 |
| `localuser0` | 只把 `x-luna-is-local-user` 从 1 改成 0 | **整曲** 6 档 |
| `no-cookie` | 只不发 Cookie | **整曲** 6 档 |
| `sig-mismatch` | URL 用时间戳设备号，签名器 `init()` 用另一个随机 16 位 | **整曲** 6 档 |
| `no-sign` | 同样的请求，不发 `x-helios` / `x-medusa` | `HTTP 200 + 0 字节` |

`rand16` 两轮的设备号与 `service-id`、`good-ts` 全都不同，结果一致。
`probe-shape` 复刻的是当初扫 7 首全试听时用的那份**设备号 + 版本号 + local-user**，
今天在同一首整曲曲目上是整曲；但 `src/probe.mjs` 实际还多发 `x-tt-trace-id` 与 `accept-encoding`，
这一条没把那两个头带上，所以它**不等于替 shipped probe 的完整请求背书**（第七节）。

上面这段是 2026-10-28 那一轮的原话，它当时**没有**对试听样曲目跑 `rand16` / `no-cookie` /
`sig-mismatch` / `captured`（预算超出最初的 15–25 次估算，多出来的都花在跨曲目复测上）。
这几条加上票里原本缺的 `captured`，在 2026-11-03 的补跑里都跑到了，见本节的后两小节。

### 换曲目，其余一切不动

| 曲目 | 曲长 | `good-ts`（时间戳） | `service-id`（固定 16 位） |
| --- | --- | --- | --- |
| 整曲样曲目 1 | 185.3 s | 整曲 6 档（lossless 1572 kbps） | 整曲 6 档 |
| 整曲样曲目 2 | 109.0 s | 整曲 6 档 | 整曲 6 档 |
| 试听样曲目 1 | 278.5 s | 60 s 试听，仅 `higher` 1 档 | 60 s 试听，仅 `higher` 1 档 |
| 试听样曲目 2 | 292.7 s | 30 s 试听，仅 `higher` 1 档 | 30 s 试听，仅 `higher` 1 档 |

试听样曲目 1 正是当初 Wine 原型里逐首扫到的那一首（60 s / 278.5 s），
两种设备号形状读数相同；免签名的 `seo-web` 对同一首回包里 `video_duration` 也是 60.001，
也就是免签名接口早把它当试听级发出来了。
（`seo-web` 的回包结构不同，本票不拿它判整曲，只用它佐证「试听长度」这个观察。）

### 真机在网线上发的是什么（2026-11-03，`tools/signer-tee.mjs`）

把本机那个已登录的播放器（sodam，登录态就存在它自己的配置里）的 `signer_url` 临时指向这台
中转，让它自己把队列跑起来，抓到 6 条签名请求。跑完把 `signer_url` 改回原来那一份，
并与备份逐字段比过一致。

抓到的 6 条签名请求，按观察项列出来是这些（每项都是 6 条共同的读数，没有例外）：

- 请求路径：`POST /luna/pc/track_v2` 四条、`POST /luna/pc/feed/song-tab` 两条。
- `device_id`：6 条全是 **13 位毫秒时间戳**，而且 6 条彼此不同。
- `iid` / `fp`：6 条都满足 `iid = device_id + 1`、`fp = device_id`。
- 请求头名：`content-type`、`cookie`、`user-agent`、`x-luna-background-type`、
  `x-luna-is-background-req`、`x-luna-is-local-user`、`x-ss-stub`。
- 公共参数：`app_name=luna_pc`、`channel=official`、`device_platform=windows`、
  `device_type=Windows`、`os_version=Windows 11`、`region=cn`、`geo_region=cn`、
  `tz_name=Asia/Shanghai`、`version_name=3.3.0`、`version_code=30030000`。
- Cookie：只记到「6 个字段」，值不落盘。

两件事一次说清：

1. **本机这条链路上没有一份稳定的「登录设备号」可供匹配。** 抓到的 6 条请求，每条都换一个
   13 位时间戳，与 `good-ts` 同形。「签名设备 = 账号登录设备」这条假说在这台机器上**没有
   可指认的那台设备**——不是没抓到，而是发出去的根本不是固定值。第六节那条客户端缺陷
   由此从「代码里读出来的回退」升级为**网线上的实测**。
2. **矩阵复刻的那一份请求，在抓包件记到的那些项上和真机一致**：头名是同一个集合（只记了名字
   与个数，没记顺序），上面列的 10 个公共参数取值也逐项相同。矩阵一共发 21 个公共参数，
   抓包件只白名单记了这 10 个——`aid`、`os_region`、`build_mode`、`cdid` 那些**没比对过**，
   这条结论的范围就到「记到的那些项」为止。
   对不上的只有一处，而且方向反过来：`src/probe.mjs` 多发 `x-tt-trace-id` 与 `accept-encoding`，
   **真机这两个头都不发**。所以 `probe-shape` 那条 arm 没复刻它们不是漏项，它比 shipped `probe`
   更接近真机（第七节）。

### 不打上游的旁证：本机播放器自己的缓存

同一个账号、同一台机器、同一个签名器，播放器走的正是「设备号 = 每请求一个毫秒时间戳」那条路径。
它的缓存条目带着播放器自己算出来的 `preview` 标记（曲目号与曲名不外传，只给计数）：

| 缓存条目 | 播放器判定 | 数量 | 中位体积 |
| --- | --- | --- | --- |
| 全部 | — | 406 | — |
| 整曲 | `preview=0` | 139 | 2.24 MB |
| 试听 | `preview=1` | 267 | 0.97 MB |

也就是说 **139 首整曲是在「设备号每请求都不同」这个条件下拿到的**，而同一条件下另有 267 首只有试听。
样本比上面那 4 首的对照大两个数量级。但它**不是对照实验**：没有控制任何变量，
它只能说明「同一套凭据条件下两种结果并存」，与「决定因素在曲目层」一致。
2026-11-03 的抓包给这句话补上了直接证据，但范围要说住：抓到的 6 条证明的是**这台播放器现在的行为**
确实是每条请求一个 13 位毫秒时间戳；那批缓存是长期攒下来的，只能算与这套行为一致，
不是那 6 条记录直接证成的。当天缓存已滚到 100 首，同一套判据下仍是两种结果并存
（试听 77 / 整曲 23），方向没变。

### 一条容易误用的字段

`track.label_info.only_vip_download` 在**整曲曲目和试听曲目上都为 `true`**，
不能拿它判断「这首曲子这个账号能不能听整曲」。能判定的仍然只有
`video_model.video_duration` 与 `track.duration` 的关系（也就是 `probe` 现在用的
`fullTrack` 判据）。它旁边那个 `only_vip_playable` 是另一回事——补跑里它只在试听级
回包出现，见上面「顺带读到一个能区分的字段」一节。

> 上面几张表里的曲目号只留在本机，不入库——它们能反出个人收听记录。
> 结论不依赖具体曲目号：换成你自己的「一首已知整曲 + 一首已知试听」照第二节跑一遍即可。
> 试听样曲目是从本机播放器缓存里挑的：每条缓存的 `.quality` 文件带着播放器自己算出的
> `preview` 标记（第 3 个字段）与体积，反推出的长度落在 30 / 60 秒就是试听——
> 本次三首样本的缓存标记与上游回包判定逐首一致。

## 四、结论

1. **「签名设备必须与账号登录设备一致」这条假说，在实测范围内不成立，且补跑之后范围更宽。**
   它的预言是「设备号与登录设备不一致 ⇒ 不给整曲」。2026-10-28 那一轮的反例有四个，都落在
   同一首有授权的曲目上：每次请求都不一样的毫秒时间戳、每轮都不同的随机 16 位、服务落盘的
   固定 16 位——这三个值都不是本机这条链路上任何一份固定身份——都拿到了整曲；甚至**根本不发 Cookie**
   （这时候压根没有登录设备可言）也拿到了整曲。一个反例就足以推翻它的普遍形式。
   当时要说清的边界是「这些反例只出现在本来就肯给整曲的曲目上」。
   **这一条现在收口了，但收口的依据要说准**：2026-11-03 把抓包来的真实身份打到两首试听级曲目
   （294.2 s / 255.1 s），读数仍是 30 / 60 秒单档，同一份身份打在有授权的曲目上照样整曲——
   而这份身份与 `good-ts` 同形，所以它不构成「又一种身份没翻盘」那种区分力。真正把它收口的是
   抓包本身：本次抓到的 6 条请求，每条都换一个 13 位毫秒时间戳，
   **本机这条链路上没有一份可指认的稳定设备号能被当成「登录设备」**——绑定说缺的不是对照，是主语。
   范围也要说清：实测的是这台机器上这条 libresoda 系链路；上游服务端有没有替这个账号登记过别的
   设备，本票没有可查的入口，所以这句是「本机无从匹配」，不是「上游没有登记」（第七节第一条）。
2. **Cookie 的有无不是变量，这条现在两类曲目都测到了。** 同一首曲目的整曲结果在带 Cookie 与
   完全不带 Cookie 时相同；补跑在试听级曲目上重做了这组对照（`no-cookie` 与其他形状同读数）。
   注意测的始终是**有无**、不是「缺哪个字段」：「Cookie 缺字段导致某些曲目降级」这个具体形态
   仍然没被直接测过（第七节）。能确定的是：**同一份 Cookie 下，A 曲目整曲、B 曲目试听**——
   这个差异不在凭据侧。
3. **「签名构造有误」不成立。** 所有带签名的 arm 都拿到结构完整的回包；
   唯独 `no-sign` 拿到 `HTTP 200 + 0 字节`。这既说明签名确实被校验，也说明
   「非空回包 = 签名被接受」这个推理在本接口上成立。
4. **真正的原因是曲目层面的授权差异，这次还读到两个对得上的字段。** 同一份凭据、同一个签名器、
   同一台机器下，有授权的曲目给出整曲全部档位（185.3 s / 109.0 s / 209.4 s 三首），
   试听级的只给 30–60 秒（四首，两轮各两首），且每首的结果与设备号形状无关。
   补跑的读数把「曲目授权」这句话落到字段上：两首试听级回包都带
   `track.label_info.only_vip_playable=true`，整曲样曲目没有这个字段；而账号自己的
   `/luna/pc/me` 回 `my_info.is_vip=false`（这条有匿名对照撑着，见第三节）。
   按字面读：**这几首是只有会员能播的曲目，而这个账号不是会员**——不是签名器换了一份设备号就被降级。
   但这是**相关，不是因果证明**：要坐实还差一份已知会员账号在同一批曲目上的对照（第七节）。
   至于当初那 7 首：**推测**全部落在试听级这一侧——逐首复测的只有其中 1 首，
   另外 5 首没复测（第七节）。但本票要回答的那件事已经有答案了：
   **不是服务自己生成的设备号造成的。**

**本票要回答的那件事可以按定案收口了**：票里那句「为什么只能拿到试听」不再靠推断——
试听级曲目上补齐了五种设备号形状与一次真实身份重放（第二节写明这一格为什么不构成新的区分力），
曲目侧的授权闸也读到了可读字段与账号档位。还挂着的两件事不再是「责任归谁」，而是
「授权具体由哪一层决定」与「一台会发固定设备号的客户端会不会改变判定」，见第七节：
前者需要一份已知会员账号在同一批曲目上的对照，后者本机没有那样的客户端。

一张票只负责分清责任。本票要回答的那件事有明确答案：**不是服务自己生成的设备号造成的**——
同一份设备号在别的曲目上照样拿到整曲。责任既不在本仓库，也不在客户端落到 URL 里的那个时间戳
（第六节那条是独立缺陷，与本票结论没有因果关系）。上游对「哪首曲子能给整曲」的判定本票不往下追
（会员层级 / 地区授权 / 单曲购买，具体是哪一种需要另一份带已知权益账号的对照）。

### 顺带被削弱的一条既有说法

`sig-mismatch`（URL 设备号与签名器设备号不一致）没有被拒。但**不能就此证明上游不校验设备一致性**：
那首曲目在不带 Cookie、不带任何一致性时本来就是整曲，这条对照没有区分力。
补跑在试听级曲目上也跑了 `sig-mismatch`，与另外五种形状同读数——同样没有区分力，
因为那首曲目在任何形状下都不给整曲。
要真正证伪「成套」要求，需要一首「只有成套才给整曲」的曲目，两轮都没找到。
本仓库继续按「签名器与 URL 用同一份设备号」实现是自洽且更省事的（避免每请求重新 `init()`），
只是**不该再把它当成上游的强制要求来写文档**。

## 五、多人共享同一份设备身份的后果

票里这条判据的前提（设备绑定）没有成立，所以这里回答的是「既然不绑定，共享身份意味着什么」。

- **权益角度：在本票实测范围内没有后果。** 整曲与否与设备号无关，共享一份身份既不会让谁的
  权益变差，也不会让任何人凭共享身份多拿到什么。这句话现在的范围包括试听级曲目：
  抓包来的真实身份在两首试听级曲目上没换来整曲（判据表倒数第二行），
  所以「换个身份能不能多拿到」这一问在两类曲目上都测过了，答案都是不能。
  反过来说，**设备身份不是访问控制**，不要指望用「每人一个设备号」来限制谁能拿到整曲。
- **上游视角下的风险：风险变大了，且集中在签名器这一台机器上。**
  签名即凭据、且账号 Cookie 不是必要变量，意味着「一个签名器 + 一个出口 IP + 一个设备号」
  可以为任意多人取任意有授权的整曲。上游看到的画像是「同一个设备号高频请求大量不同曲目」——
  这是最典型的爬虫特征，被风控时受影响的是这台签名器与它的 IP，而不是某个用户。
  这正是本仓库总纲里「删掉会替别人打上游的诊断接口、按 IP 分桶限流」那两个决定的理由所在。
- **可接受的共享形态**：一个签名器只服务一小撮可预期的人（家庭/小团队），
  并把速率限制在自己的容量与画像可解释的范围内。公开池化一台签名器，等于把自己的 IP
  押上去替所有人承担风控。

## 六、确实指向客户端的那件事（与本票结论无关，但是独立缺陷）

调查过程中在代码层面确认了一件事。先说清楚：它**不是**试听问题的原因（第四节 1 已经排除），
所以本票的结论不依赖它；但它是一个独立存在的缺陷，归属在那两个客户端仓库，
本票只负责把它记下来，**改法由那两个仓库决定**。

- `libresoda` 的 `device_id` / `iid` / `fp` 配置项默认为空，空值会落到
  `Date.now()` 与 `Date.now()+1`（见该仓库 `src/soda/mod.rs` 的 `pc_app_params_with`），
  于是**每个请求的设备号都不一样**；`sodam` 的设置界面没有这三个字段可填，
  所以普通用户一直走的是这条回退路径（本机日志里能直接看到 `device_id=""`）。
  2026-11-03 的抓包把这从代码推断升级为网线实测：6 条请求、6 个互不相同的 13 位毫秒时间戳，
  `iid = device_id + 1`、`fp = device_id` 与该函数的回退逐字一致（第三节）。
  顺带一条给那两个仓库的更正：`sodam-core` 现在的代码里其实有 `SODA_DEVICE_ID` 这类环境变量入口
  （该仓库 `crates/sodam-core/src/config.rs`），缺的是设置界面——本票没测已安装的 0.3.7 认不认它。
- 会造成的影响有两层，都属于「画像」而不是「权益」：
  一是上游会看到「同一台机器、同一 Cookie、设备号每请求一变」；
  二是签名器每次都要重新 `init()`（本仓库 `src/bdms.mjs` 按设备号变化重新初始化），
  而按早前原型的观察，`init()` 之后有一段「短签名窗口」。
  本次读数里 `X-Medusa` 多数落在 828、少部分是 840——**本票没有把这组长度归因到那个窗口**：
  矩阵里每条 arm 都先签一次丢掉、只用第二次的那一份（`signWarmedUp`），
  所以这些长度到底是窗口尾部还是稳态，本次的对照设计测不出来。
  能说的只有一句：这些签名全部被上游接受了，但那只覆盖 `track_v2` 一条接口。
- 要动哪儿，供那两个仓库参考（不是本票的决定）：`sodam` 缺一个能持久化设备身份的入口；
  `libresoda` 的空值回退目前产生「每请求新值」，而这个值本不需要每请求都换。
  至于应该「每进程一个」「落盘一个」还是「缺了就拒绝并提示」，那是那边的接口设计，本票不预判。

## 七、未决项

原先挂着的三条已经在 2026-11-03 的补跑里关掉：`captured` 那一格（两首试听级曲目 + 一首整曲曲目）、
`SODA_QR_STATE` 那条路径（不用走——真机发的根本不是那份身份）、以及「试听级只测了两种形状」
（`rand16` / `no-cookie` / `sig-mismatch` 都补到了同一首试听级曲目上，逐字同读数）。
剩下的：

- 抓包件只覆盖**这台机器上这一个登录态**，而且抓的是本机那个 `libresoda` 系播放器：官方 PC 客户端
  这台机器没装（只有安装包与解包件）。所以「真机没有稳定的登录设备号」这句话实测到的是这条链路。
  2026-11-07 的复核在同一链路又抓到 5 条（全 PC 端点、三号齐全；同一件连读两次的坐标没有漂，
  见第三节的「2026-11-07 复核」），这条样本边界不变。
  两台都能再往前推一步，但本机都做不到：一台**会发固定设备号**的客户端（官方 PC 客户端，
  或填了 `SODA_DEVICE_ID` 的）才能给「固定 vs 变化」这组对照补上真实主语；
  而「成套」那条要求要测出区分力，还得有一首「只有成套才给整曲」的曲目（第四节末），也没找到。
- 「Cookie 字段不全」这个具体形态没测（两轮都只测了有无）。
- 顶替只发生在**手打那份**上：只给 `--device`、不给 `--iid` / `--fp` 时，缺哪个就拿 `device_id` 顶哪个
  （脚本按缺的字段逐个提醒）——那不是一份完整的抓包身份。`--from-capture` 这条路既顶不了也不将就：
  件里那条三样都得是真机原值，缺一个就不采用，并报出是第几行、那条 `at` 何时。只跑 `captured` 时当场
  `exit 2`；跑整份矩阵时只跳过这一条 arm、打同一句理由，其余照跑（与「压根没给身份」同一个后果）。
  身份字段只收字符串（数字的字面在 JSON 解析时就被改写过，`1e15` 与 `…0` 都保不住），`at` 只认 ISO 时刻——都是「不把工具自己编的值发出去」。
  `--device` / `--iid` / `--fp` 与 `--from-capture` 也不能同时给，同时给在参数校验阶段就拒，
  报错只点名这次真给了的那几个号；`--名字=值` 与 `--名字 值` 两种写法等价。
- `probe-shape` 没带上 shipped `probe` 多发的 `x-tt-trace-id` 与 `accept-encoding`。补跑给出的
  新事实是：**真机这两个头都不发**，所以这一条只是「arm 与 shipped probe 不同形」，
  不是「arm 与真机不同形」。要替 `probe` 本身背书，得再补一条带这两个头的 arm。
- 曲目层的授权具体由哪一层决定（会员层级 / 地区 / 单曲购买）——`only_vip_playable` 与
  `is_vip=false` 是相关的，不是因果证明：需要一份已知会员账号在同一批曲目上的对照。
  顺带一句已经测到的：非会员账号在免费曲目上照样拿得到整曲 6 档含 lossless，
  所以「整曲」与「会员曲目」不是一回事。
- 「只有成套才给整曲」的曲目是否存在，即上游到底校不校验设备一致性——见第四节末。
- 当初那 7 首里有 5 首没逐首复测（第四节 4）。
- 其它接口（不止 `track_v2`）上签名有效性是否同样宽松。
  抓包看到的一个线索：真机也在给 `POST /luna/pc/feed/song-tab` 求签名。
- **WSL 容器里第一次调用签名会挂住 —— 已定位（#30），是挂载位置，不是这条路不支持**：
  `libmssdk:local` 镜像、`--entrypoint bash` 覆盖掉入口、`wineboot -u` 也手工补过，
  `wine node.exe tools/entitlement-matrix.mjs --arm captured` 仍然 6 分钟无输出、只能 `docker rm -f`。
  #30 那条复现命令把仓库目录整个 `-v` 进容器，而仓库在这台机器上位于 Windows 盘——`bdms.node` 就是从
  `/mnt/*` 这类 drvfs 绑定挂载上被加载的。分层探针 `verify/wine-multi/bdms-layers.mjs` 把卡点钉在
  **加载模块**这一层：本次那一次只打 `step=begin` 与 `step=load` 两行就没了，`init` 与签名两层
  根本没开始（外层 `timeout -s KILL 45` 切断回 `rc=137`）；同一份模块换进容器自己的文件系统，
  三层 1.5 秒（TTY）/ 3.2 秒（重定向到文件）走完。工具那一次没分层，卡点是按同一挂载形状推的。
  第三节那批补跑读数仍出自本机 Windows 原生 Node（与容器里是同一个 `bdms.node`）——换到容器里重跑
  同样的 arm 属于复现，不构成新的对照，但现在这条路是通的：容器内的跑法（`--arm good-ts`、
  曲目号当场编、`--cookie-from` 指一个空文件＝匿名，上游回 `HTTP 200` 非空回包）与探针的实测秒数
  写在 `verify/wine-multi/README.md` 的「已知的环境坑」。**那次只是通路验证，不是权益读数**——
  合成曲目号加匿名 cookie 下 `fullTrack` 本来就该是 false，别把它当成一条新的权益证据。
  仍然没查出来的两件事：#30 里记的 `timeout 180` 切不断（本次 `timeout -s KILL` 与对整个进程组发
  TERM 都切得断，为什么默认信号不行没测）；覆盖 entrypoint 之后 prefix 初始化程度是否另有影响
  （本次用过的两个卷都先跑过一次 `wineboot -u`，全新没初始化的卷没测）。
- 输出脱敏覆盖到的形态有离线测试钉住（带空格的用户名、`Program Files`、无冒号的容器路径、
  盘根、首段带空格的 posix、单段路径、UNC）。代价是相对路径也会被一并隐掉——诊断时少点线索，
  换的是日志可以放心外贴。
- `probe` 的试听提示文案按本结论改掉了「设备指纹不匹配」这一归因。现在可行动的那一句
  已经读得到（这首是「仅会员可播」的曲目，而账号 `is_vip=false`），但要把它写进提示
  就得让 `probe` 多打一次 `/luna/pc/me`——出网面因此扩大一张票的量，本票不做。

## 八、敏感边界

- Cookie 只在本机进程内使用，不写盘、不打日志、不进任何输出文件；输出里只出现「几个字段」。
- 签名值只记长度；设备号只留首尾三位；曲目号只留末四位、曲名不输出
  （`tools/entitlement-matrix.mjs` 的读数默认就是脱敏的，日志可以直接贴进票里）。
- 取证中转（`tools/signer-tee.mjs`）落盘的那份抓包件是**唯一**写着完整真实设备号的地方：
  POSIX 上 0600（NTFS 不认这个位，见下一条）、默认只绑回环、`--out` 指到仓库目录里会被直接拒。
  用完删掉，别贴进票里——
  `--from-capture` 就是为「不用把设备号抄上命令行」准备的。
  「仓库外」只是位置下限：`chmod 0600` 在 Windows 的 NTFS 上不生效（代码里注明了），
  网盘同步目录与漫游配置这类会被复制走的地方尤其要避开。Cookie 与 `Authorization` 的值、
  `x-helios` / `x-medusa` 都不进那份文件，离线用例把这条钉住了。
- 连报错都做了脱敏：`bdms.node 不存在：<本机绝对路径>` 这类信息在输出里只留失败步骤，
  绝对路径整段隐掉（Windows、容器里无冒号的 posix 路径、首段带空格的路径都覆盖）。
- 本文不含任何曲目号、Cookie、签名值或完整设备号；读数只说明响应形状。
- 把这份结论贴到 issue / PR 时，同样不要带 Cookie、签名值、完整设备号或本机路径。
